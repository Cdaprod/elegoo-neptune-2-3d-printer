# Motion timeline and server-side print history

Neptune Observatory maintains one server-side timeline alongside the shared
MKS polling worker. It uses the existing serialized printer transport and does
not add a second connection or poller. Print recording continues while the
browser is closed.

## Feedrate over time

The Motion page uses a fixed-height, responsive chart with elapsed time on X and
feedrate in mm/min on Y, starting at zero. Its rolling view offers 5 minute,
15 minute, 1 hour, and 24 hour windows, pointer panning, wheel/button zoom, and
a time cursor. Event lines are clipped to the plot; the separate event strip is
bounded to five labels, so event count cannot increase chart height.

The curve is explicitly **planned/estimated**, never measured motor speed:

- A matching active SD print maps MKS progress samples onto the analyzed
  G-code plan. This is an estimate, not a report of the executing instruction.
- Fixed, acknowledged jog operations contribute a bounded planned profile from
  their dispatch time and requested feedrate. An `ok` is not treated as
  completion evidence; the estimated duration is labeled accordingly.
- When fresh firmware state reports idle, persisted poll timestamps produce a
  zero line labeled as firmware-state evidence, not motor feedback. No idle
  history is fabricated before the service has collected samples.
- If none of those sources provides at least two usable samples, the chart
  displays an honest empty state.

Feedrate history is bounded to 1,200 representative points. Minima, maxima,
first/last samples are retained when longer ranges are downsampled, preserving
short stops and peaks. Timeline points carry source and confidence labels.
The fixed-height plot keeps a consistent size on desktop and mobile.

## G-code analysis and offline demonstration

On Digital Twin > Simulation, selecting an OrcaSlicer G-code file loads it in
the browser for 3D rendering and sends its text to the authenticated Observatory
API for server-side motion analysis. The server stores a SHA-256 reference and
parsed segments; this is an upload to Observatory for analysis only, not to the
printer SD card. The built-in offline movement sequence is analyzed once by the shared backend
interpreter. Motion consumes its feedrate timeline and the Digital Twin consumes
those same analyzed segments for toolhead, bed, and deposited-path replay.

The built-in movement demo is generated by the same backend interpreter from a
small fixed G-code sequence with three moves and explicit dwells. It is available
even before a user G-code file is analyzed. Motion > Feedrate can load the demo
curve, while Digital Twin > Simulation > Load offline movement demo renders the
same sequence. The fixture is not stored as a print file or sent to the printer.

The interpreter handles `G20`/`G21`, `G90`/`G91`, `M82`/`M83`, `G92`, `G28`,
`G0`/`G1`, `M201`/`M204` acceleration settings, and `G4` dwells. A file's
`G28` is only a simulated coordinate reference and creates no fabricated path;
`G92` changes logical offsets, not physical movement. Arc moves `G2`/`G3` are
omitted with a warning. When acceleration is present, straight-line
trapezoidal/triangular timing is estimated; otherwise the estimate assumes
constant commanded feedrate with start/stop boundaries. Firmware planner
look-ahead, jerk, pauses, and exact execution timing are not modeled.

The offline checkbox uses this fixed interpreter-backed fixture and does not
communicate with the printer. The Twin can load the same server-interpreted
segments from its Simulation page. Movement rises above zero and returns to zero
between moves and during explicit dwells. Historical playback uses backend
print-session telemetry and a matching G-code file where available. Without a
matching file, the session remains telemetry-only. Re-select the matching
G-code in the Twin for toolpath reconstruction.

## Stored data and limits

The shared poller stores timestamps, printer state, temperatures, progress,
poll latency, and operation evidence in `/data/neptune-observatory.db`. Idle
state samples are stored separately from print-session samples so the live
feedrate chart can show only observed idle intervals. When a print becomes idle,
its final telemetry sample is retained in that session and closes the planned
feedrate curve at zero. All this runs in the FastAPI service without Safari.

Retention is bounded: completed sessions expire after 30 days; at most 100,000
telemetry rows, 100 command events, 8 analyzed G-code files, 200,000 motion
segments, and 1,200 rendered feedrate samples are retained. These limits bound
the SQLite database on the persistent Compose data volume.

API endpoints (all require dashboard authentication):

- `GET /api/timeline`: sessions, analyzed G-code metadata, bounded planned
  history, live print telemetry, and feedrate history.
- `GET /api/timeline/offline-demo`: a fresh, interpreter-generated demonstration
  path for the Motion chart and Digital Twin; it is not persisted as a printer
  file or telemetry.
- `GET /api/timeline/sessions/{id}`: stored samples and progress-mapped
  estimated feedrate for historical playback.
- `POST /api/timeline/gcode`: accepts a filename and text body (up to 50 MB)
  for analysis only; it sends no G-code to the printer.

## Source distinctions and verification

Firmware-reported M114 samples remain unavailable: the earlier one-shot query
returned only `ok`. The position cards therefore stay empty instead of using
zeros. Operator-observed home references are discrete events and do not create
paths. The prior 0.1 mm X jog remains inconclusive. No new physical query or
printer-control action is part of this timeline implementation.

Automated tests use temporary SQLite databases and mocked printer snapshots.
They cover modal G-code state, offsets, homing references, acceleration/dwells,
idle feedrate samples, min/max downsampling, backend session persistence, and
acknowledged jog labeling.
